# RE-RecSys-Inspired Real-Estate Recommendation System

An end-to-end, **RE-RecSys-inspired** recommendation system for Indian real
estate, built as an academic Recommendation Systems project. It implements
the paper's four-user-category architecture (cold-start / short-term /
long-term / short-long-term → rule-based / content-based / hybrid
content+collaborative) on top of a **public property-listings dataset**,
with fully transparent **simulated** user interactions.

> **This is not a reproduction of Housing.com's production system.** See
> [Academic Integrity](#academic-integrity--how-this-differs-from-the-original-re-recsys-paper)
> below before reading any numbers in this document.

## 1. Problem Statement

Real-estate platforms list far more properties than any one user can browse.
A recommendation system that narrows this down using a user's stated
preferences and (when available) their browsing behaviour improves both
customer satisfaction and platform conversion — exactly the problem the
RE-RecSys paper addresses for Housing.com.

## 2. Research Paper

**RE-RecSys: An End-to-End system for recommending properties in Real-Estate
domain** — Venkatesh C, Harshit Oberoi, Anil Goyal, Nikhil Sikka
(Housing.com, India), CODS-COMAD 2024. [arXiv:2404.16553](https://arxiv.org/abs/2404.16553)

The paper classifies users into 4 categories (cold-start / short-term /
long-term / short-long-term) and routes each to a rule-based, content-based,
or hybrid content+collaborative model, trained on Housing.com's proprietary
property database and Google-Analytics clickstream (160,000 sampled users,
Jan–Jun 2022). It evaluates with MAP@6 and NDCG, and reports <40ms inference
latency at 1000 requests/minute in production.

## 3. Motivation

Reproducing RE-RecSys's *architecture* on a public dataset is a good way to
learn the full recommendation-systems stack — rule-based cold-start
handling, content-based cosine similarity, ALS matrix factorization, hybrid
combination, and offline evaluation — without needing access to proprietary
production data.

## 4. Academic Integrity — How This Differs From the Original RE-RecSys Paper

| | **Original paper (Housing.com)** | **This project** |
|---|---|---|
| Property data | Proprietary internal relational DB | Public listings ZIP (4 Indian cities) |
| User data | Real Google Analytics clickstream (1B+ clicks/month) | **100% SIMULATED** interactions (see below) |
| Sample size | 160,000 real users, Jan–Jun 2022 | 1,200 synthetic user personas |
| Environment | Production, serving 1000 rpm | Local, single-machine, academic |
| Collaborative filtering | Apache Spark ALS (cluster) | `implicit` ALS (single machine — see §13) |
| Reported results | Real-world MAP@6/NDCG, <40ms latency | Simulated-environment MAP@6/NDCG, local latency benchmark |

**We do not claim to reproduce Housing.com's results.** Every dataset
inspection finding, every synthetic-data-generation decision, and every
number in `results/` is produced by code in this repository, not copied
from the paper. Nowhere does this project compare our simulated-environment
numbers directly against the paper's production numbers as if they were
equivalent.

### Why the interactions are synthetic

The attached dataset (`data/raw/*.csv`) contains **property listings only**
— no user accounts, sessions, or clicks. Every user profile
(`data/processed/users.csv`) and every interaction
(`data/processed/interactions.csv`) is generated by
`src/users/generate_users.py` / `src/interactions/generate_interactions.py`,
which are fully documented, deterministic (seeded), and designed so that
simulated interactions correlate with how well a property matches a user's
*stated* preferences (plus a configurable amount of random "exploration").
**No real user was involved in producing this data.** Any recommendation
quality numbers below describe how well the models perform against this
simulated ground truth, not real-world conversion.

## 6. Dataset

Raw ZIP: 4 city CSVs (`mumbai.csv`, `gurgaon_10k.csv`, `hyderabad.csv`,
`kolkata.csv`, **38,502 rows combined, 4 different raw schemas**) +
`facets/` id→label lookup tables. Full inspection notes, including a
significant discovery about the `TRANSACT_TYPE` field's real semantics, are
in **[`docs/data_dictionary.md`](docs/data_dictionary.md)** — read this
before touching the code.

After `src/data/prepare.py`: **38,482 properties**, 4 cities, harmonized
into one canonical schema (`data/processed/properties.csv`).

| City | Buy | Rent | Median Buy Price | Median Rent (₹/mo) |
|---|---|---|---|---|
| Mumbai | ~6,867 | ~2,632 | ₹1.70 Cr | ₹20,000 |
| Gurgaon | ~10,152 | ~552 | ₹2.30 Cr | ₹60,000 |
| Hyderabad | ~7,910 | ~1,573 | ₹93.5 L | ₹48,000 |
| Kolkata | ~7,059 | ~1,737 | ₹60 L | ₹18,500 |

### Dataset limitations
* Facet id→label lookup tables only fully cover the Gurgaon export; ids from
  the other 3 cities are decoded as `Other:<id>` where unmatched.
* No image counts, no dealer/owner profile type — both used by the paper's
  cold-start cohorts — are reliably present, so the rule-based cohort
  definition is adapted (see `config.yaml`).
* This is a **snapshot** of listings, not a time series — there is no way to
  derive real "recency" from it, hence the synthetic-interaction approach.

## 7. RE-RecSys Methodology → Our Implementation

| Paper component | Adaptation | Where |
|---|---|---|
| 4 user categories (thresholds in interaction-time-minutes) | Same 4 categories, thresholds in interaction **counts** (no real timestamps available) | `config.yaml: user_category_thresholds`, `src/users/categorize.py` |
| Rule-based cold-start (cohort: locality × apt-type × profile-type × price/sqft bin × area bin) | Cohort: locality × property_type × bhk × transaction_type (no reliable profile_type field) | `src/models/rule_based.py` |
| Content filtering, cosine similarity, categorical+numeric binned features | Same binning idea, bins re-derived from our data's actual distributions | `src/features/property_features.py`, `src/models/content_based.py` |
| Interaction weight table (Table 1, from real conversion rates) | 7 interaction types mapped onto our public-site model, same low→high intent ordering | `config.yaml: interaction_weights` |
| ALS collaborative filtering (Apache Spark ML) | ALS via `implicit` (single-machine; Spark is unnecessary at our ~38K-item scale) | `src/models/collaborative.py` |
| Hybrid = avg(content, collaborative) | Same, alpha configurable/tunable (paper uses fixed average) | `src/models/hybrid.py` |
| MAP@6, NDCG evaluation | Same metrics **+** Precision/Recall/HitRate @5/10/20 | `src/evaluation/` |
| <40ms production latency @1000rpm | Local latency benchmark (not claimed production-equivalent) | `scripts/evaluate.py`, `results/tables/latency_benchmark.csv` |

## 8. Models

1. **Rule-Based** (`src/models/rule_based.py`) — weighted preference-match
   score (budget/location/BHK/property-type/furnishing/amenities) + cohort
   popularity from simulated interaction aggregates. Used for cold-start.
2. **Content-Based** (`src/models/content_based.py`) — property vectors
   (one-hot categorical + multi-hot amenities + TF-IDF description, 830
   dims), user profile = weighted sum of interacted property vectors,
   ranked by cosine similarity. Used for short-term.
3. **Collaborative Filtering** (`src/models/collaborative.py`) — implicit
   ALS matrix factorization on the weighted user×property interaction
   matrix.
4. **Hybrid** (`src/models/hybrid.py`) — `alpha * content + (1-alpha) *
   collaborative`, alpha configurable / tunable. Used for long-term and
   short-long-term.

All 4 are orchestrated by `src/recommendation/orchestrator.py`, which
classifies the user's category and routes automatically.

## 9. Evaluation Methodology

Per-user **leave-last-N-out** split (`src/evaluation/split.py`): the most
recently generated 30% of each user's interactions become the held-out test
set; the rest is train. Models used for evaluation are refit **on the train
split only** — verified leak-free by `tests/test_evaluation.py`. Metrics:
Precision@K, Recall@K, MAP@K, NDCG@K, HitRate@K at K∈{5,10,20} (plus K=6 to
mirror the paper's reporting).

## 10. Results (simulated evaluation environment — see §4)

Produced by `python scripts/evaluate.py` against 1,200 synthetic users / 38,482
properties / 15,559 simulated interactions (10,888 train / 4,671 test).

### Model comparison @K=10

| Model | Precision@10 | Recall@10 | MAP@10 | NDCG@10 | HitRate@10 |
|---|---|---|---|---|---|
| Rule-Based | 0.0140 | 0.0191 | 0.0085 | 0.0207 | 0.1200 |
| Content-Based | 0.0073 | 0.0112 | 0.0036 | 0.0098 | 0.0667 |
| Collaborative | 0.0027 | 0.0038 | 0.0010 | 0.0032 | 0.0267 |
| Hybrid | 0.0047 | 0.0060 | 0.0014 | 0.0048 | 0.0400 |

Full table incl. K=5/20: `results/tables/model_comparison.csv`.

### Hybrid alpha sweep @K=6 (best alpha by NDCG: **0.9**)

alpha=0.9 (mostly content) narrowly edges out alpha=1.0 (pure content) and
clearly beats the pure-collaborative end (alpha=0.0) on this simulated
population — see `results/tables/hybrid_alpha_sweep.csv` and
`results/plots/12_hybrid_alpha_sweep.png`.

### Category-wise / city-wise / weighting-scheme ablation

See `results/tables/category_performance.csv`,
`results/tables/city_performance.csv`,
`results/tables/weighting_scheme_ablation.csv` (paper Table-3-style
comparison of linear / exponential-decay / TF-IDF interaction weighting).

### Latency (local benchmark — NOT the paper's production claim)

| Model | mean (ms) | median (ms) | p95 (ms) |
|---|---|---|---|
| Collaborative | 0.71 | 0.70 | 0.81 |
| Rule-Based | 30.9 | 31.9 | 38.7 |
| Hybrid | 32.9 | 37.6 | 59.6 |
| Content-Based | 47.9 | 59.5 | 89.9 |

### Discussion

Rule-based scores highest — expected, since the same preference-match
function that generates our simulated interactions is also used by the
rule-based scorer, so it has a structural advantage on this synthetic
ground truth (documented, not hidden). Absolute scores are low across all
models: K≤20 against thousands of city-level candidates, a single held-out
test interaction per short-history user, and the deliberate 30%
"exploration" negative sampling built into the interaction simulator
(`config.yaml: synthetic.negative_sample_ratio`) all make this a genuinely
hard top-K task — see [Limitations](#12-limitations).

## 11. Installation & Running

```bash
git clone <this-repo>
cd project

python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate

pip install -r requirements.txt
```

### Dataset setup
Raw CSVs are already included under `data/raw/` (mumbai.csv, gurgaon_10k.csv,
hyderabad.csv, kolkata.csv, `facets/`). No manual download needed.

### Train (reproducible, one command)
```bash
python scripts/train.py
```
Runs: data prep → synthetic users → synthetic interactions → content
feature engineering → ALS training. Produces every artifact under
`data/processed/` and `models/`. Takes ~30s on a laptop.

### Evaluate
```bash
python scripts/evaluate.py
```
Writes `results/tables/*.csv` and `results/metrics/summary.json`.

### Generate plots
```bash
python scripts/generate_plots.py
```
Writes 15 PNGs to `results/plots/`.

### Run the backend
```bash
uvicorn src.api.main:app --reload
```
API docs at `http://127.0.0.1:8000/docs`.

### Run the frontend
```bash
streamlit run app/frontend/app.py
```

### Run tests
```bash
pytest -q
```
56 tests covering parsing, feature engineering, synthetic data generation,
all 4 models, the orchestrator, evaluation metrics/leakage, and every API
endpoint. All pass against the artifacts produced by `scripts/train.py`.

## 12. Limitations

* Simulated interactions, not real behaviour (see §4) — absolute metric
  values should not be read as "real-world accuracy".
* Facet id→label coverage is partial for 3 of 4 cities (§6).
* No real timestamps → "recency" is a simulated flag, not wall-clock time.
* `implicit` ALS (single machine) instead of Spark ALS — appropriate at this
  dataset's scale (~38K items) but would need re-architecting for the
  paper's 1.1M-property / 3M-user scale.
* Short-term/cold-start category metrics in this run are exactly 0 for some
  slices (`results/tables/category_performance.csv`) — with only 1 held-out
  interaction per short-history user against thousands of candidates at
  K=6, and 30% of ground-truth interactions being deliberate non-preference
  "exploration" clicks, this is a genuinely hard, high-variance regime with
  a small evaluation sample (see §10 Discussion) rather than a broken model
  — `tests/test_models.py` independently confirms every model returns
  sensible, non-empty, correctly-ranked output for cold-start/short-term
  users.

## 13. Future Work

* Larger synthetic population + more interactions per user for
  lower-variance evaluation.
* Learned (not fixed-grid) hybrid alpha, e.g. via a small ranking model.
* Session-based / sequential models for genuinely time-aware short-term
  recommendations.
* Full facet coverage for Mumbai/Hyderabad/Kolkata via a richer lookup
  source.
